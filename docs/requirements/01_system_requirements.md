## 1. 기획 의도 (v2에서 범위 정밀화)

### 1.1 배경·목적 (변경 없음)
소규모 뷰티샵의 전화·수기 예약 → 이중예약·노쇼 관리 부재·통계 활용 불가.
시술·디자이너·일시 선택 온라인 예약 + 관리자 상태 관리 + 자동화 리포트/대시보드.

### 1.2 범위 (조건 1·2·3 반영 — "CRUD" 표현 제거, 기능 열거로 정밀화)

**In:**
- 회원: LOCAL 가입·로그인, KAKAO 간편 로그인
- 예약: **생성 · 본인 조회 · 본인 취소(상태 CANCELED 전환) · 관리자 상태 변경** (수정·물리 삭제 없음)
- 시술·디자이너: 고객 조회 + 관리자 등록·수정·삭제 (예약 참조 시 삭제 거부)
- 고객 관리: **목록 · 상세 · 이메일 검색까지만**
- REST API(조회 전용) + Python 리포트 스크립트 1종·산출물 1종 + Streamlit 대시보드(지표 3종)

**Out (확정):**
- 결제, 알림톡, 다중 지점
- **GOOGLE 로그인** (미결 ② 확정: Enum에서 제외, LOCAL·KAKAO만)
- 예약 내용 수정, 예약 물리 삭제
- 고객 수정·삭제·차단
- 노쇼 자동 판정 스케줄러 (미결 ③ 확정: ADMIN 수동 처리만)
- 계정 통합 (동일인의 LOCAL·KAKAO 계정 연동)

## 3. SR — 시스템 요구사항 (v2: 기능 SR 16건 + NFR 2건으로 재편)

### 3-1. 회원/인증

**SR-01 (←UR-01) LOCAL 가입·로그인** [조건 6]
- 가입 시 `provider=LOCAL`, `provider_id=NULL` 저장
- email은 DB UNIQUE 제약, 비밀번호는 bcrypt 해싱, Spring Security formLogin
- 검증: 가입→로그인 성공 / 중복 이메일 가입 시 오류 메시지

**SR-02 (←UR-02) KAKAO 간편 로그인** [v3 확정]
- 인가코드→토큰→사용자정보 3단 교환. 실제 회원 식별은 반드시 `(provider, provider_id)` 조합으로 수행한다.
- 카카오가 이메일 미제공 시 또는 수신 이메일이 기존 email과 충돌 시,
  `kakao_{정규화된 provider_id}@kakao.local` 대체 이메일을 저장한다.
  - provider_id는 이메일 로컬파트 허용 문자([a-z0-9])로 정규화하여 삽입
  - 대체 이메일은 시스템 내부 식별용이며 로그인 ID로 사용하지 않음
  - 화면·리포트에서 `@kakao.local` 이메일은 "카카오 회원"으로 표시, 원문 비노출
- LOCAL 회원가입에서는 `@kakao.local` 도메인(시스템 예약 도메인) 이메일 가입을 거부한다.
- 검증: ①정상 카카오 로그인 ②이메일 미제공 로그인 ③기존 LOCAL 동일 이메일 카카오 로그인
  ④LOCAL 가입 폼 `x@kakao.local` 입력 → 거부 — 4케이스

**SR-03 (←UR-03) 권한 접근 제어**
- `/admin/**` → ADMIN만, 예약 신청·내 예약 → 인증 사용자만, 서버사이드(Security 설정) 제어
- 검증: USER 계정으로 /admin URL 직접 접근 시 403 또는 로그인 리다이렉트

### 3-2. 조회 (고객)

**SR-04 (←UR-04) 시술 목록 화면** — 이름·가격·소요시간(분)·설명 표시
**SR-05 (←UR-05) 디자이너 목록 화면** — 이름·전문분야·소개 표시
- 검증(공통): 등록 데이터가 화면에 전건 렌더링

### 3-3. 예약

**SR-06 (←UR-06) 예약 생성**
- 시술·디자이너·날짜(LocalDate)·시간(LocalTime)·메모 입력, 초기 상태 REQUESTED
- 검증: 생성 후 reservation 행에 status=REQUESTED

**SR-07 (←UR-06) 이중예약 차단** [조건 5 / 미결 ① 확정]
- 충돌 판정: 같은 디자이너·같은 날짜의 `REQUESTED`·`CONFIRMED` 예약 중
  `기존 시작 < 신규 종료 AND 신규 시작 < 기존 종료` (종료 = 시작 + 시술 duration)
- 충돌 시 저장 거부 + 폼 오류 메시지
- 검증: 10:00~11:00(60분 시술) 존재 시 10:30 신청 → 거부 / 11:00 신청 → 허용 / CANCELED 예약과 겹침 → 허용

**SR-08 (←UR-07) 내 예약 조회**
- 로그인 회원 **본인** 예약만 목록 표시 (member_id = 로그인 회원)
- 검증: A 로그인 시 B의 예약이 목록에 없음

**SR-09 (←UR-08) 본인 예약 취소**
- 소유자 서버사이드 검증 후 상태를 CANCELED로 전환 (REQUESTED·CONFIRMED에서만 가능)
- 검증: 본인 취소 성공 / 타인 예약 취소 요청(URL 직접 호출) 시 거부

### 3-4. 관리자

**SR-10 (←UR-09) 예약 상태 전이 관리** [조건 4 / 미결 ③ 확정]
- 허용 전이표 (이외 전이는 모두 거부):

| 현재 | 허용 전이 | 조건 |
|---|---|---|
| REQUESTED | → CONFIRMED, CANCELED | - |
| CONFIRMED | → COMPLETED, CANCELED, NO_SHOW | NO_SHOW는 예약 시작시각 경과 시 ADMIN 수동 처리 |
| COMPLETED / CANCELED / NO_SHOW | (종료 상태, 전이 불가) | - |

- 검증: 전이표의 허용 5경로 성공 + 금지 전이(예: COMPLETED→CONFIRMED) 거부

**SR-11 (←UR-10) 시술·디자이너 관리** [조건 2]
- ADMIN이 시술·디자이너를 등록·수정·삭제
- **삭제 정책: 예약(상태 무관)이 참조 중인 시술·디자이너는 삭제 거부 + 안내 메시지**
- 검증: CRUD 4동작 + 예약 참조 데이터 삭제 시도 → 거부 확인

**SR-12 (←UR-11) 고객 조회** [조건 3]
- ADMIN이 고객 목록·상세 조회, 이메일 부분일치 검색 (수정·삭제·차단 없음)
- 검증: 목록 표시 / 상세 진입 / 이메일 검색 결과 일치

**SR-13 (←UR-09) 관리자 예약 목록 검색·페이징** [조건 7]
- 검색 조건 3개: 회원명, 디자이너명, 상태
- 상태 필터 값: REQUESTED, CONFIRMED, COMPLETED, CANCELED, NO_SHOW (5종)
- 페이징 10건/페이지
- 검증: 3조건 각각 검색 결과 일치 + 상태 필터 5값 동작 + 11건 이상 시 2페이지 생성

### 3-5. API/자동화

**SR-14 (←UR-13 데이터 공급) REST API** [조건 7]
- `GET /api/reservations` — ADMIN 권한, JSON 배열, 필드: id, memberName, serviceName, designerName, reservationDate, reservationTime, status
- 인증 [v3 확정]: 서비스 계정 + 세션 쿠키 방식 — ADMIN 권한 서비스 계정(`report_bot`)으로
  `POST /login` 수행 → 세션 쿠키 유지한 채 API 호출
- 검증: 쿠키 없는 호출 401/403, 서비스 계정 로그인 후 호출 200 + 필드 7종 확인

**SR-15 (←UR-13) 리포트 자동 생성** [조건 7 / 범위통제]
- Python 스크립트 **1종**이 SR-14 API를 호출해 기간별·시술별·디자이너별 집계를 담은
  **Markdown 리포트 1종**을 `reports/YYYYMMDD_report.md`로 저장
- 실행 주체 [v3 확정]: ADMIN이 터미널 명령어로 수동 실행 (`python report.py --from --to`).
  스케줄러·화면 버튼은 Out.
- 검증: 명령 1회 실행 → 파일 생성 + 집계 수치가 DB 직접 집계와 일치

**SR-16 (←UR-12) Streamlit 대시보드** [조건 7]
- 지표 3종: ①기간별 예약 건수 추이(선) ②시술별 건수(막대) ③디자이너별 건수(막대)
- 필터: 기간(시작일~종료일)
- 검증: 3차트 렌더링 + 필터 적용 시 수치가 DB 집계와 일치

### 3-6. NFR (비기능 요구사항) [조건 8]

**NFR-01 (보안)** — DB 비밀번호·OAuth secret 등 민감정보는 환경변수로 분리, 코드·설정 하드코딩 금지 ✅ D1 적용 완료
- 검증 [v3 확정]: 3층 비밀 스캔 — ①추적 파일 `git grep` ②미추적 파일 파일시스템 검색
  (`Get-ChildItem`+`Select-String` 또는 동급 스캐너) ③스테이징 인덱스 `git grep --cached` — 3층 모두 0건

**NFR-02 (성능)** — 관리자 예약 목록 1페이지(10건) 조회 시 실행 SQL **3개 이하**
- 측정 범위 [v3 확정]: 인증 완료 후, 관리자 예약 목록의 Repository/Service 호출 시작부터
  목록 렌더링 데이터 취득 완료까지 실행된 SQL만 측정 (인증·세션 쿼리 제외)
- 검증: hibernate SQL 로그 카운트 (구현 방식 LAZY+fetch join은 SA 문서 소관)

## 5. v1 → v2 변경 이력

| 조건 | 반영 내용 |
|---|---|
| 1 | 범위 "예약 CRUD" → 생성·본인조회·본인취소·관리자 상태변경 열거 |
| 2 | SR-11 신설 (시술·디자이너 CRUD + 예약 참조 삭제 거부) |

| 5 | SR-07 duration 구간 겹침 공식 + 충돌 대상 상태(REQUESTED·CONFIRMED) |
